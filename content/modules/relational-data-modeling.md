# Modelling data: keys, relationships and shape

Schema design decisions are the hardest to reverse. Code gets refactored every
sprint; a badly shaped table with two years of data in it does not. This guide
covers the modelling decisions you will actually make on a CRUD app, and the
ones interviewers ask you to justify.

## Keys

**Primary key** — uniquely identifies a row. Two reasonable choices:

| | Sequential integer | UUID |
|---|---|---|
| Size | 8 bytes | 16 bytes |
| Index behaviour | Appends cleanly | Random inserts fragment a clustered index |
| Leaks information | Yes — volume, and enumerable | No |
| Generated by | The database | Anywhere, including the client |

Sequential ids let anyone see you have 412 customers, and let them walk
`/orders/1`, `/orders/2` looking for a missing authorization check. UUIDs avoid
both but cost index performance. **Sequential UUIDs** (UUIDv7, or SQL Server's
`NEWSEQUENTIALID`) give you most of both.

Being able to compare them is the interview answer; either choice is fine.

**Natural vs surrogate keys.** A natural key is real data (an email, an ISBN). A
surrogate is meaningless (an auto-increment id). Prefer surrogates: real-world
values change, and cascading an email change through five foreign keys is
misery. Keep the natural value as a unique *constraint*, not as the key.

## Relationships

**One-to-many** — the foreign key lives on the many side.

```sql
orders.customer_id REFERENCES customers(id)
```

**Many-to-many** — a join table with both foreign keys and a composite primary
key:

```sql
CREATE TABLE enrolments (
  student_id BIGINT REFERENCES students(id),
  course_id  BIGINT REFERENCES courses(id),
  enrolled_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  grade      TEXT,
  PRIMARY KEY (student_id, course_id)
);
```

Note the extra columns. The join table is the natural home for attributes *of
the relationship itself* — this is why a comma-separated column or a JSON array
is not an acceptable substitute.

**One-to-one** — usually a sign the tables should be one table. Legitimate
reasons to split: optional data you rarely load, or columns with different
security requirements.

## Foreign keys are worth having

Application-level checks race and get bypassed by scripts, admin tools and
migrations. The constraint is the only thing that actually holds.

Decide the delete behaviour explicitly:

- `ON DELETE RESTRICT` (default in most engines) — refuse to delete a parent
  that still has children. Usually what you want.
- `ON DELETE CASCADE` — delete the children too. Correct for genuinely owned
  data (order line items), dangerous for anything else.
- `ON DELETE SET NULL` — for optional relationships.

And index your foreign keys. An unindexed FK makes a cascading delete scan the
child table for every parent row.

## Normalisation, and when to break it

Third normal form, in practice: **every fact lives in exactly one place.**

If a customer's email is stored on the customer *and* copied onto every order,
you have two problems: updating it requires touching many rows, and until you
do, the data disagrees with itself.

Deliberate exceptions that are correct:

- **A price at time of sale.** An order line must store the price it was sold
  at. If it joins to the product for the current price, last year's invoices
  change when you run a sale. This is not denormalisation — it is a different
  fact.
- **A cached counter** (`comment_count`) when the count is read constantly and
  the join is expensive. Accept that it can drift and have a way to recompute.
- **A flattened read model** for search or reporting, kept in sync
  asynchronously.

The rule: **normalise by default, denormalise with a reason you can state.**
"For performance" is not a reason unless you measured.

## Soft deletes

`deleted_at TIMESTAMPTZ NULL` instead of a real DELETE.

Upsides: recoverable, keeps referential history, satisfies "who deleted this".

Downsides that people underestimate:

- Every single query must remember `WHERE deleted_at IS NULL`. Forget once and
  you leak deleted data.
- Unique constraints break — you cannot re-register an email whose old row is
  still there. Solutions get ugly (partial indexes, or a nullable
  discriminator).
- It conflicts with "delete my data" obligations.

Use it where recovery genuinely matters. Do not apply it to every table by
reflex.

## Audit columns

`created_at`, `updated_at`, and often `created_by`, `updated_by`. Cheap to add
at the start, painful to backfill. Add them.

For anything where the *history* matters — financial records, permission
changes — consider an append-only event or audit table instead of mutating a
row and losing what it was.

## Enums and status columns

Three options for `orders.status`:

1. **A text column with a CHECK constraint** — simple, readable in queries,
   easy to extend. Good default.
2. **A lookup table** — lets you attach metadata (display name, sort order,
   is_terminal) and enforces the FK. Good when the set is business data.
3. **A native enum type** — enforced, compact, and genuinely painful to alter
   in Postgres. Avoid unless the set will never change.

Whichever you choose, the set of statuses is a state machine. Write down the
legal transitions somewhere, because "how did an order get from `cancelled` to
`shipped`" is a real production question.

## JSON columns

Modern databases have real JSON support with indexing. Legitimate uses:

- Genuinely schemaless data (a third-party webhook payload you store verbatim)
- Per-tenant custom fields
- A denormalised read cache

Bad uses: anything you filter, join or aggregate on regularly, and anything with
a stable shape. A JSON blob is a schema you have decided not to write down, and
the database cannot enforce or index it well.

## Multi-tenancy

If your app serves multiple organisations, decide early:

- **Shared tables with a `tenant_id` column** — simplest, cheapest. Every query
  and every index must include the tenant. A single missing filter is a data
  breach.
- **Schema per tenant** — better isolation, harder migrations at scale.
- **Database per tenant** — strongest isolation, most operational cost.

Most SaaS products start with the first. If you do, enforce it centrally — a
global query filter or row-level security — rather than trusting every developer
to remember.

## Naming

Consistency beats any particular convention:

- `snake_case` in the database, mapped to the language's convention in code
- Plural table names (`orders`), singular column names (`status`)
- Foreign keys named `<table>_id`
- Booleans read as assertions: `is_active`, `has_shipped`
- Timestamps end in `_at`; dates end in `_on`

## Working through a modelling question

Interviewers hand you a domain — "model a library" or "model an e-commerce
checkout" — and watch how you think. A structure that works:

1. **List the nouns.** Book, Copy, Member, Loan, Reservation.
2. **Say which are entities and which are values.** An address might be either.
3. **Draw the relationships and their cardinality out loud.** "A Book has many
   Copies; a Loan is one Copy to one Member for a period."
4. **Name the constraints.** A Copy can be on at most one active Loan. A Member
   has a borrowing limit.
5. **Ask what changes over time.** Does a Loan get updated, or does a Return
   create a new record? That question decides whether you have history.
6. **Only then, columns and types.**

The single best signal you can give is asking clarifying questions before
drawing tables — because it is what the job actually requires.
